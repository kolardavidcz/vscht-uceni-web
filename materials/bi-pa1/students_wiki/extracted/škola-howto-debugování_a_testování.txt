Debugování GDB Návod pro práci s GDB: Debugování v Linuxu (GDB) Valgrind Valgrind je skvělý debugovací nástroj, který je vlastně mnoho nástrojů v jednom. Memcheck memcheck umožňuje hledat chyby v práci s pamětí, chybné uvolňování, apod. Dostatečně užitečný výstup lze získat voláním valgrindu takto: valgrind -v --leak-check=full --show-reachable=yes --track-origins=yes <váš program> <parametry vašeho programu> Stejně jako v případě GDB, i zde je velmi žádoucí kompilovat program s parametrem -g , čímž jsou do vzniklé binárky přidány debugovací symboly, které umožní získávat i čísla řádků kódu, a ne pouze informaci, ve kterém souboru k chybě došlo. Poměrně pěkný a přehledný popis toho, co jednotlivé chyby znamenají, je k nalezení v dokumentaci nástroje memcheck, v sekci 4.2: 4.2. Explanation of error messages from Memcheck , nemá asi smysl jej překládat. Helgrind helgrind slouží pro odhalení problémů způsobených při práci s POSIX thready , konkrétně deadlocks (nekonečné čekání na nespnitelnou podmínku), race conditions/data races (současný přístup k jedné proměnné více vlákny) a nesprávné použití funkcí API (předávání špatných parametrů, apod.). valgrind --tool=helgrind <váš program> <parametry vašeho programu> I v případě helgrindu se vyplácí testovaný program kompilovat s přiložením debugovacích symbolů (parametr -g u gcc). Massif Massif slouží pro profilování heapu a stacku. Vykreslí informace o tom kolik místa na stacku/heapu jste si naalokovali a akutálně máte naalokováno. valgrind --tool=massif <program> <parametry> Předchozí volání vyplivne soubor massif.out.<PID>, v němž jsou zobrazeny informace. Ty vypíšete pomocí ms_print massif.out.<PID> Testování Nástroje jako např. Valgrind jsou naprosto na nic v momentě, kdy neexistují testy, které by dostatečně pokryly kód programu. Důvod je ten, že jde o nástroje, které provádějí kontroly výhradně runtime, tedy za běhu programu – vidí pouze chyby, ke kterým došlo během toho jednoho běhu. Ani v tom nejchybovějším kódu Valgrind nic nenajde, když se ten kód vůbec nespustí. Proto je nutné psát dostatečně široké testy. Ačkoliv je to naprosto očividné, ještě před psaním testů je nutné si pečlivě rozmyslet, co se vlastně od testovaných funkcí chce. Neměla by existovat žádná šedá oblast, kde si člověk řekne „Hmm, ale já vlastně nevím, co od toho chci za právě téhle kombinace hodnot!“. Velmi hrubě se dá říct, že testy by mely pokrývat: Všechny (netriviální) funkce/metody, a to i jejich varianty. Veškeré kombinace booleanovských vstupů. Několik příkladů vstupů, které mají být určitě správně, a funkce má vracet úspěch. Příklad: funkce my_strcmp(), která má fungovat obdobně jako strcmp() ze standardní knihovny: my_strcmp ( "ahoj" , "ahoj" ) ; /* => ma vracet true. Pokud nevraci true, je to spatne. */ Několik příkladů vstupů, které mají být určitě špatně, a funkce má vracet neúspěch. Příklad: my_strcmp ( "ahoj" , "svete" ) ; /* => ma vracet false. Pokud nevraci false, je to spatne. */ my_strcmp ( "ahoj" , NULL ) ; /* => Pokud je v zadani definovano, ze druhy argument muze byt NULL, nesmi dojit k segfaultu! */ Několik příkladů hraničních hodnot – hodnot, které jsou blízko a na hranici, kde se mění chováni funkce. Příklad, funkce my_abs(), která má vracet absolutní hodnotu čísla (ačkoliv funkce my_abs() je očividně triviální, jasně ukazuje, co je taková hraniční hodnota): my_abs ( 1 ) ; /* => 1, pokud ne, je to spatne */ my_abs ( 0 ) ; /* => 0, pokud ne, je to spatne */ my_abs ( - 1 ) ; /* => 1, pokud ne, je to spatne */ Několik příkladů extrémních hodnot. Například prázdný řetězec, NULL, velmi nízká nebo naopak velmi vysoká čísla, apod. Priklad: my_strcmp ( "" , "svete" ) ; my_strcmp ( "ahoj" , NULL ) ; /* => Viz bod 4) */ my_strcmp ( "ahoj" , "sveteeeeee [... dalsich sest kilobajtu dat ...]" ) ; Snaha by měla být pokrýt testy co možná největší podíl zdrojového kódu. V Linuxu existuje součást GCC, která se jmenuje gcov , a umožňuje snadno získat code coverage. Funguje to tak, ze se při spuštění aplikace kontroluje, jaka část kódu byla provedena a jaká nikoliv. Je nutné si uvědomit, ze i při stoprocentním pokrytí řádek kódu není vše vyhráno. Příklad: int my_2_div_x ( int x ) { return 2 / x ; } int my_test ( ) { /* * Tento test potvrdi funkcnost, ponevadz 2 / 2 = 1. */ return ( my_2_div_x ( 2 ) == 1 ) ; } Ačkoliv tento příklad kontroluje 100 % řádek kódu, nekontroluje všechny chyby. V tomto případě neodhalí to, ze funkce my_2_div_x způsobí division by zero chybu v momentě, kdy se jí jako vstup předá nula. Proto ani stoprocentní code coverage není definitivní spása.
